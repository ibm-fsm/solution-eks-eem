Phase 1: Foundation & Prerequisite Configuration

Published

March 25, 2026

MD  Mat Davis 


Before deploying the IBM Event Endpoint Management (EEM) operator, the infrastructure foundation must be secured. This phase covers provisioning the certificate manager, establishing the ingress layer, and configuring the external Identity Provider (IdP).

1.0 Create Namespace

Create the dedicated namespace for the EEM deployment. It is recommended to set your current context to this namespace to simplify subsequent commands.

# 1. Create the namespace
kubectl create namespace ibm-eem

# 2. Set as current context (Optional but recommended)
kubectl config set-context --current --namespace=ibm-eem

1.1 Certificate Manager

EEM relies heavily on Cert-Manager for internal mTLS communication between the Manager, Gateway, and Portal components.

  • Option A: Production (Generic)
  • Option B: Lab (Install)

On standard Kubernetes platforms, utilize an existing Certificate Manager installation.

Requirements:

  • Version: v1.12+ recommended.
  • APIs: Must support Issuer.cert-manager.io/v1 and Certificate.cert-manager.io/v1 GroupVersionKinds (GVK).
  • Alternative: If Cert-Manager is not allowed, you must manually create certificates for all components and provide them via Kubernetes secrets (complex).

For lab environments (e.g., k3s) where Cert-Manager is not yet present, install it via Helm.

# 1. Add the Jetstack repository
helm repo add jetstack https://charts.jetstack.io
helm repo update

# 2. Install Cert-Manager
helm install \
  cert-manager oci://quay.io/jetstack/charts/cert-manager \
  --version v1.19.2 \
  --namespace cert-manager \
  --create-namespace \
  --set crds.enabled=true

1.2 Ingress Configuration

The Ingress Controller is the entry point for both API traffic (Gateway) and User traffic (Portal/Manager). The Gateway specifically requires SSL Passthrough to handle raw mTLS handshakes directly from Kafka clients.

  • Option A: Production (AWS EKS)
  • Option B: Lab (Nginx)

Target: AWS EKS utilizing the AWS Load Balancer Controller.

In EKS, the AWS Load Balancer Controller provisions Application Load Balancers (ALBs) for Ingress resources and Network Load Balancers (NLBs) for Service resources. Because ALBs do not support SSL passthrough, routing for IBM Event Endpoint Management (EEM) components must be handled as follows:

  • EEM Manager (UI and APIs): The ingresses related directly to the EEM manager, which include the UI and other API endpoints, exclusively use HTTP/HTTPS. For these components, an Ingress generating an AWS ALB can be used and is fully supported.
  • Gateway Groups: When gateway groups are defined, an NLB with SSL passthrough is needed. This will require defining a Kubernetes Service (type LoadBalancer) with the appropriate AWS annotations when the gateway is deployed so that the proper NLB path is created. Even though the gateway deployment will also define an Ingress that might generate an ALB path, that specific ALB path can be ignored.

Install the Nginx Ingress Controller using Helm. The publishService flag is crucial for ensuring the LoadBalancer IP is correctly populated in Ingress statuses.

# 1. Add the Nginx repository
helm repo add ingress-nginx [https://kubernetes.github.io/ingress-nginx](https://kubernetes.github.io/ingress-nginx)
helm repo update

# 2. Install the Controller
helm install nginx-ingress ingress-nginx/ingress-nginx \
  --namespace ingress-nginx \
  --create-namespace \
  --set controller.kind=DaemonSet \
  --set controller.service.type=LoadBalancer \
  --set controller.publishService.enabled=true \
  --set controller.extraArgs.enable-ssl-passthrough=true \
  --set controller.allowSnippetAnnotations=true

1.3 DNS & Networking

Ensure your Identity Provider (Keycloak) and EEM endpoints are resolvable.

  • Requirement: The OIDC provider (e.g., keycloak.eem.gym.lan) must be accessible via DNS from inside the cluster pods.
  • Lab Setup: Use a wildcard DNS entry or edit your /etc/hosts file to point the desired hostname to the IP address of your ingress controller.
TipCoreDNS Caching

If you make changes at the networking level (like /etc/hosts on the nodes) and pods do not pick it up, reboot CoreDNS to flush the cache.

kubectl -n kube-system rollout restart deployment coredns

1.4 Identity Provider (Keycloak)

EEM does not manage users internally; it requires an OIDC-compliant Identity Provider. Follow these steps to configure Keycloak for the lab.

A. Realm & Client Setup

  1. Log in: Access Keycloak (e.g., admin/admin) and create a new realm called ibm-eem.
  2. Create Client: Go to Clients > Create Client.
    • Client type: OpenID Connect
    • Client ID: eem-portal
    • Name: IBM Event Endpoint Management
    • Click Next.
  3. Capability Config:
    • Client authentication: On (This enables “Confidential” access type).
    • Authorization: Off (EEM handles authorization mapping).
    • Authentication flow: Select Standard flow and Direct access grants.
    • Click Next.
  4. Login Settings:
    • Root URL: (Leave blank)
    • Home URL: https://eem-portal.gym.lan
    • Valid redirect URIs: https://eem-portal.gym.lan/*
      • Note: The wildcard * is recommended for labs to cover various callback paths (e.g., /callback, /auth/callback).
    • Web origins: +
    • Click Save.
  5. Capture Credentials:
    • Go to the Credentials tab.
    • Copy the Client Secret. You will need this for the EEM installation phase.

B. User Creation

  1. Create User: Go to Users > Add user.
    • Username: admin-user
    • Email: admin@example.com (Crucial: Toggle Email Verified to On).
    • First Name: John
    • Last Name: Doe
    • Click Create.
  2. Set Password:
    • Go to the Credentials tab.
    • Click Set password.
    • Password: password
    • Temporary: Toggle to Off (Prevents forced reset on first login).
    • Click Save.

1.5 Create Image Pull Secret

You must provide credentials to pull the IBM container images.

  • Option A: Private Registry (Air-Gapped)
  • Option B: IBM Registry (Lab)

Target: Restricted / Production

If pulling from an internal Artifactory that requires authentication:

kubectl create secret docker-registry ibm-entitlement-key \
  --docker-server=artifactory.internal.corp \
  --docker-username=<SERVICE_ACCOUNT> \
  --docker-password=<TOKEN> \
  -n ibm-eem
ImportantAnonymous Artifactory Access

If your internal Artifactory is configured for anonymous pulls, and you plan to manually update the Helm values.yaml to point to this local registry, do not create this secret.

Creating a dummy ibm-entitlement-key secret when anonymous access is allowed will force the cluster to attempt authentication, which will fail and result in ImagePullBackOff errors.

Target: Sandbox / POC with Internet Access

Create a secret using your IBM Entitlement Key.

# 1. Get your key from https://myibm.ibm.com/products-services/containerlibrary
# 2. Create the secret
kubectl create secret docker-registry ibm-entitlement-key \
  --docker-server=cp.icr.io \
  --docker-username=cp \
  --docker-password=<YOUR_IBM_ENTITLEMENT_KEY> \
  --docker-email=user@example.com \
  -n ibm-eem
