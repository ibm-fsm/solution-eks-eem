Phase 2: EEM Deployment

Published

March 5, 2026

MD  Mat Davis 


In this phase, we deploy the Event Endpoint Management (EEM) operator and instantiate the management cluster. The configuration must bridge the gap between the Kubernetes Service (ClusterIP) and the Ingress layer, ensuring traffic remains encrypted and OIDC authentication flows are correctly established. For complete configuration options, default values, and platform-specific mandates, please consult the official IBM Event Endpoint Management installation guide.

2.1 Configure Helm Repository

Before deploying the operator, add the IBM Helm repository to your local client.

# 1. Add the IBM Helm Repo
helm repo add ibm-helm https://raw.githubusercontent.com/IBM/charts/master/repo/ibm-helm

# 2. Update to ensure you have the latest chart versions
helm repo update

# 3. Verify the chart is available (Target: 11.7.1+)
helm search repo ibm-eem-operator

2.2 Install the EEM Operator

The EEM Operator manages the lifecycle of the Manager, Gateway, and Portal components.

Step 1: Install Custom Resource Definitions (CRDs)

  • Option A: Air-Gapped (Direct Download)
  • Option B: Connected (Direct Install)

Target: Restricted / Production

If your cluster cannot reach the public Helm repositories directly, download the chart archive using curl and install it from the local file.

# 1. Download the chart archive
curl -LO https://raw.githubusercontent.com/IBM/charts/master/repo/ibm-helm/ibm-eem-operator-crd-11.7.1.tgz

# 2. Install from the local file
helm install eem-crds ./ibm-eem-operator-crd-11.7.1.tgz \
  --namespace ibm-eem \
  --create-namespace

Target: Sandbox / POC with Internet Access

If your environment has outbound internet access, install directly from the IBM Helm repository.

helm install eem-crds ibm-helm/ibm-eem-operator-crd \
  --namespace ibm-eem \
  --create-namespace \
  --version 11.7.1

Step 2: Install the Operator

  • Option A: Air-Gapped (Local Configuration)
  • Option B: Connected (Direct Install)

Target: Restricted / Production

If pulling images from an internal Artifactory, you must download the chart, extract it, and modify the values.yaml file to point the operator to your local registry.

# 1. Download the chart archive
curl -LO https://raw.githubusercontent.com/IBM/charts/master/repo/ibm-helm/ibm-eem-operator-11.7.1.tgz

# 2. Extract the archive
tar -xzf ibm-eem-operator-11.7.1.tgz

Configure Local Registry Paths: Open ibm-eem-operator/values.yaml in your preferred text editor.

  1. Locate the public and private repository blocks at the top of the file and replace the IBM registry URLs with your internal Artifactory path.
  2. In the images block, replace the strict @sha256:... digests with the standard version tag (e.g., :11.7.1).
  3. If your Artifactory is configured for anonymous access, clear the operatorImagePullSecret value so the cluster does not attempt to authenticate.

Example configuration using a local lab Artifactory:

public:
  repo: artifactory.gym.lan:8443
  path: docker-local/ibm-eventendpointmanagement/
private:
  repo: artifactory.gym.lan:8443
  path: docker-local/ibm-eventendpointmanagement/

images:
  operator: ibm-eventendpointmanagement-operator:11.7.1
  eemManager: eim-backend:11.7.1
  egw: ibm-eventendpointmanagement/egw:11.7.1
  tutorialegw: egw-tutorial:11.7.1

# Clear this value if your registry allows anonymous pulls
operatorImagePullSecret: ""

Install the Operator: Once your values are saved, run the install command against the local directory.

# 3. Install from the local extracted directory
helm install eem-operator ./ibm-eem-operator \
  --namespace ibm-eem

Target: Sandbox / POC with Internet Access

If your environment has outbound internet access, install directly from the IBM Helm repository.

helm install eem-operator ibm-helm/ibm-eem-operator \
  --namespace ibm-eem \
  --version 11.7.1
TipVerification

Verify the operator is running before proceeding.

kubectl get deploy ibm-eem-operator -n ibm-eem
# Expected: 1/1 READY

2.3 Create OIDC Security Assets

EEM requires several Kubernetes secrets to be pre-provisioned for OIDC authentication and TLS trust.

1. OIDC Client Secret

This secret contains the credentials for your Identity Provider (Keycloak).

# Replace 'your-client-secret' with the value from Keycloak
kubectl create secret generic oidc-client-secret \
  --namespace ibm-eem \
  --from-literal=client-id='eem-portal' \
  --from-literal=client-secret='your-client-secret'

2. OIDC Trust Secret (Self-Signed Only)

If your Keycloak instance uses a self-signed certificate (common in labs), you must export its CA cert and mount it into EEM.

# 1. Download the cert from the Keycloak endpoint
echo | openssl s_client \
  -showcerts \
  -servername keycloak.my-haproxy.gym.lan \
  -connect keycloak.my-haproxy.gym.lan:443 2>/dev/null | \
  openssl x509 -outform PEM > keycloak.pem

# 2. Create the trust secret
kubectl create secret generic keycloak-trust-secret \
  --namespace ibm-eem \
  --from-file=ca.crt=keycloak.pem

2.4 Create and Import the TLS Certificate

For this EKS pilot environment, we will generate a self-signed TLS certificate to secure the EEM Manager endpoints exposed via the AWS Application Load Balancer (ALB).

Important: In a production environment, you should always request and use real, CA-signed certificates for your endpoints. However, for this lab demonstration, we will generate a self-signed certificate that includes the necessary Subject Alternative Names (SANs) to ensure all internal API communication and UI routing function correctly.

1. Generate a SAN-Enabled Certificate

Use openssl to generate a self-signed certificate and private key. The -addext flag explicitly injects the multi-level subdomains required for the internal Gateway-to-Manager routing.

# Generate a new private key and SAN-enabled certificate
openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout local-test.key -out local-test.crt \
  -subj "/O=LabEnvironment/CN=*.local.test" \
  -addext "subjectAltName=DNS:*.local.test,DNS:eem-ui.local.test,DNS:eem.eem-server.local.test,DNS:eem-gateway.local.test,DNS:eem-admin.local.test"

2. Import the Certificate into AWS ACM

The AWS Load Balancer Controller requires the certificate to reside in AWS Certificate Manager (ACM). Use the AWS CLI to import the files.

Note: You must use the fileb:// prefix so the CLI reads the raw binary bytes of the PEM file, preventing formatting corruption.

aws acm import-certificate \
  --certificate fileb://local-test.crt \
  --private-key fileb://local-test.key \
  --region us-east-1

3. Retrieve the Certificate ARN

Upon successful import, the AWS CLI will output the Amazon Resource Name (ARN) of your new certificate. It will look similar to this:

{
    "CertificateArn": "arn:aws:acm:us-east-1:123456789012:certificate/abcd-1234-efgh-5678"
}

Copy this CertificateArn value. You will need to paste it into the ALB ingress annotations in the upcoming EEM Custom Resource deployment step.

2.6 Configure Local DNS Resolution

Because we are using the generic .local.test domain for this pilot, public DNS servers will not know how to route your browser to the EKS cluster. You must manually map the EEM Manager hostnames to the Application Load Balancer (ALB) IP addresses on your local workstation.

1. Retrieve the ALB Hostname Get the external address of your EEM Manager ingress resource:

kubectl get ingress -n ibm-eem

Locate the ADDRESS column, which will contain a long AWS hostname (e.g., k8s-ibmeem-default-xxxxx.us-east-1.elb.amazonaws.com).

2. Resolve the ALB IP Addresses The local hosts file requires IPv4 addresses, not AWS hostnames. Use your terminal to resolve the ALB hostname into its underlying IP addresses:

nslookup <your-alb-hostname>

AWS ALBs typically return two or more IP addresses. You only need to copy one of them for the next step.

3. Update your Workstation Hosts File

Open your local hosts file as an Administrator or root user:

  • Windows: C:\Windows\System32\drivers\etc\hosts
  • Mac/Linux: /etc/hosts

Add a new line at the bottom mapping the resolved IP address to your EEM Manager subdomains:

# IBM EEM EKS Pilot
34.234.x.x  eem-ui.local.test eem.eem-server.local.test

Save the file. Your workstation browser will now securely route traffic directly to the AWS ALB.

2.7 Configure User Roles

When deploying your EEM instance, you must grant initial access to the system. The configuration depends entirely on your chosen authentication method.

  • Option A: OIDC Auth (UUID Mapping)
  • Option B: Local Auth (Credentials & Mapping)

Use Case: External Identity Provider (Keycloak, Auth0, etc.)

By default, an OIDC user has no permissions upon first login. You must map the Identity Provider’s user subject (UUID) directly to the EEM roles.

1. Create the Mapping File: Create a file named myroles.json and replace the id below with your Keycloak User UUID.

{
  "mappings": [
    {
      "id": "130ea2d9-e60c-4f28-8499-386ecda2d825",
      "roles": [
        "admin",
        "author"
      ]
    }
  ]
}

2. Patch the Roles Secret: Inject this JSON directly into the user-roles secret managed by the operator.

kubectl patch secret eem-manager-ibm-eem-user-roles \
  --namespace ibm-eem \
  --type='json' \
  -p="[{\"op\" : \"replace\" ,\"path\" : \"/data/user-mapping.json\" ,\"value\" : \"$(cat myroles.json | base64 -w 0)\"}]"

Use Case: Built-in Local Directory

For local authentication, you must first define the user credentials, and then map that new user ID to the appropriate roles.

1. Create the Credentials File: Create a file named myusers.json with your desired administrator credentials.

{
    "users": [
        {
            "username": "eemadmin",
            "password": "Password1$"
        }
    ]
}

2. Patch the Credentials Secret: Inject the user definition into the credentials secret.

kubectl patch secret eem-manager-ibm-eem-user-credentials \
  --namespace ibm-eem \
  --type='json' \
  -p="[{\"op\" : \"replace\" ,\"path\" : \"/data/user-credentials.json\" ,\"value\" : \"$(cat myusers.json | base64 -w 0)\"}]"

3. Create the Mapping File: Create a file named myroles.json mapping your new username to the administrative roles.

{
  "mappings": [
    {
      "id": "eemadmin",
      "roles": [
        "admin",
        "author"
      ]
    }
  ]
}

4. Patch the Roles Secret: Inject the mapping JSON into the user-roles secret.

kubectl patch secret eem-manager-ibm-eem-user-roles \
  --namespace ibm-eem \
  --type='json' \
  -p="[{\"op\" : \"replace\" ,\"path\" : \"/data/user-mapping.json\" ,\"value\" : \"$(cat myroles.json | base64 -w 0)\"}]"
TipVerification

Navigate to your configured UI host (e.g., https://eem-portal.gym.lan or https://portal.eem.corp). Log in with your Keycloak or Local credentials. You should see the Administration and Manage menu items, confirming that the role mapping was successful.

Note: The role mapping might take a few minutes to propagate. If you see an “Unauthorized” message, wait a moment and refresh.
