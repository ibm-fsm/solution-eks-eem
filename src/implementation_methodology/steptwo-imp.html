Phase 2: EEM Deployment

Published

February 20, 2026

MD  Mat Davis 


In this phase, we deploy the Event Endpoint Management (EEM) operator and instantiate the management cluster. The configuration must bridge the gap between the Kubernetes Service (ClusterIP) and the Ingress layer, ensuring traffic remains encrypted and OIDC authentication flows are correctly established. For complete configuration options, default values, and platform-specific mandates, please consult the official IBM Event Endpoint Management installation guide.

2.1 Configure Helm Repository

Before deploying the operator, add the IBM Helm repository to your local client.

# 1. Add the IBM Helm Repo
helm repo add ibm-helm https://raw.githubusercontent.com/IBM/charts/master/repo/ibm-helm

# 2. Update to ensure you have the latest chart versions
helm repo update

# 3. Verify the chart is available (Target: 11.7.1+)
helm search repo ibm-eem-operator

2.2 Install the EEM Operator

The EEM Operator manages the lifecycle of the Manager, Gateway, and Portal components.

Step 1: Install Custom Resource Definitions (CRDs)

helm install eem-crds ibm-helm/ibm-eem-operator-crd \
  --namespace ibm-eem \
  --create-namespace \
  --version 11.7.1

Step 2: Install the Operator

helm install eem-operator ibm-helm/ibm-eem-operator \
  --namespace ibm-eem \
  --version 11.7.1 \
  --set webhook.create=true \
  --set watchAnyNamespace=false
TipVerification

Verify the operator is running before proceeding.

kubectl get deploy ibm-eem-operator -n ibm-eem
# Expected: 1/1 READY

2.3 Create Security Assets

EEM requires several Kubernetes secrets to be pre-provisioned for OIDC authentication and TLS trust.

1. OIDC Client Secret

This secret contains the credentials for your Identity Provider (Keycloak).

# Replace 'your-client-secret' with the value from Keycloak
kubectl create secret generic oidc-client-secret \
  --namespace ibm-eem \
  --from-literal=client-id='eem-portal' \
  --from-literal=client-secret='your-client-secret'

2. OIDC Trust Secret (Self-Signed Only)

If your Keycloak instance uses a self-signed certificate (common in labs), you must export its CA cert and mount it into EEM.

# 1. Download the cert from the Keycloak endpoint
echo | openssl s_client \
  -showcerts \
  -servername keycloak.my-haproxy.gym.lan \
  -connect keycloak.my-haproxy.gym.lan:443 2>/dev/null | \
  openssl x509 -outform PEM > keycloak.pem

# 2. Create the trust secret
kubectl create secret generic keycloak-trust-secret \
  --namespace ibm-eem \
  --from-file=ca.crt=keycloak.pem

2.4 Deploy the EEM Instance

We use a Custom Resource (CR) to define the EEM instance. Select the configuration that matches your environment.

  • Option A: Production (Generic)
  • Option B: Lab (Self-Signed)

Use Case: Standard deployment with valid CA-signed certificates.

Create a file named eem-instance-prod.yaml:

apiVersion: events.ibm.com/v1beta1
kind: EventEndpointManagement
metadata:
  name: eem-manager
  namespace: ibm-eem
spec:
  license:
    accept: true
    license: 'L-CYBH-K48BZQ'
    metric: VIRTUAL_PROCESSOR_CORE
    use: EventAutomationProduction
  manager:
    endpoints:
      - name: ui
        host: portal.eem.corp
      - name: gateway
        host: gateway.eem.corp
      - name: admin
        host: admin.eem.corp
      - name: server
        host: server.eem.corp
    authConfig:
      authType: OIDC
      oidcConfig:
        clientIDKey: client-id
        clientSecretKey: client-secret
        discovery: true
        secretName: oidc-client-secret
        site: 'https://keycloak.eem.corp/realms/ibm-eem'
    # Mount the custom CA cert to trust Keycloak
    tls:
      trustedCertificates:
        - certificate: ca.crt
          secretName: keycloak-trust-secret
    storage:
      storageClassName: gp3
      type: persistent-claim

Apply the Configuration:

kubectl apply -f eem-instance-prod.yaml

Use Case: Lab environment needing custom trust anchors and local storage.

Create a file named eem-instance-lab.yaml:

apiVersion: events.ibm.com/v1beta1
kind: EventEndpointManagement
metadata:
  name: eem-manager
  namespace: ibm-eem
spec:
  license:
    accept: true
    license: 'L-CYBH-K48BZQ'
    metric: VIRTUAL_PROCESSOR_CORE
    use: EventAutomationProduction
  manager:
    endpoints:
      - name: ui
        host: eem-portal.gym.lan
      - name: gateway
        host: eem-gateway.gym.lan
      - name: admin
        host: eem-admin.gym.lan
      - name: server
        host: eem.eem-server.gym.lan
    authConfig:
      authType: OIDC
      oidcConfig:
        clientIDKey: client-id
        clientSecretKey: client-secret
        discovery: true
        secretName: oidc-client-secret
        site: 'https://keycloak.my-haproxy.gym.lan/realms/eem-portal'
    # Mount the custom CA cert to trust Keycloak
    tls:
      trustedCertificates:
        - certificate: ca.crt
          secretName: keycloak-trust-secret
    storage:
      storageClassName: local-path
      type: persistent-claim

Apply the Configuration:

kubectl apply -f eem-instance-lab.yaml
NoteStartup Time

The Operator will now provision the PostgreSQL database, API Manager, and Gateway pods. This process can take 5-10 minutes. Watch the status with: kubectl get pods -n ibm-eem -w

2.5 Configure User Roles

By default, the OIDC user has no permissions. You must map the Keycloak user subject (UUID) to the EEM admin role.

1. Create the Mapping File: Replace the id below with your Keycloak User UUID.

{
  "mappings": [
    {
      "id": "130ea2d9-e60c-4f28-8499-386ecda2d825",
      "roles": [
        "admin",
        "author"
      ]
    }
  ]
}

2. Patch the Secret: We inject this JSON directly into the user-roles secret managed by the operator.

# Save the JSON to a file named 'myroles.json' first
kubectl patch secret eem-manager-ibm-eem-user-roles \
  --namespace ibm-eem \
  --type='json' \
  -p="[{\"op\" : \"replace\" ,\"path\" : \"/data/user-mapping.json\" ,\"value\" : \"$(cat myroles.json | base64 -w 0)\"}]"
TipVerification

Navigate to https://eem-portal.gym.lan (or your configured host). Log in with your Keycloak credentials. You should see the Administration and Manage menu items, confirming that the role mapping was successful.

Note: The role mapping might take a few minutes to propagate. If you see an “Unauthorized” message, wait a moment and refresh.
