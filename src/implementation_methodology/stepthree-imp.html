Phase 3: Gateway Deployment

Published

March 17, 2026

MD  Mat Davis 


With the EEM Manager and Gateway pods running, the next phase is establishing the data plane. The Gateway requires a backend Kafka cluster to route traffic to, and a Layer 4 network path to accept incoming mTLS/TLS client connections.

3.1 Backend Kafka Provisioning

The EEM Gateway acts as a secure proxy and requires a target Kafka cluster to manage.

  • Option A: Production (Bring Your Own Kafka)
  • Option B: Lab (Bitnami)
  • Option C: Lab (Strimzi Operator)

Use Case: Connecting to an existing enterprise Kafka environment (e.g., AWS MSK, Confluent Cloud, or IBM Event Streams).

Ensure you have the following information from your Kafka administrators:

  • Bootstrap server addresses.
  • Authentication credentials (e.g., SASL/PLAIN, SASL/SCRAM, or mTLS client certificates).

Use Case: Spinning up a temporary, lightweight Kafka broker in your k3s environment to validate Gateway routing with secure SSL connections (but without the complexity of Mutual TLS).

We can deploy a single-node Kafka instance using the Bitnami Helm chart, secured by a local Certificate Authority.

1. Generate the Local Certificates First, create the SSL certificates to secure the broker traffic:

# Create the Certificate Authority
openssl req -x509 -newkey rsa:4096 -days 365 -nodes -keyout ca.key -out ca.crt -subj "/CN=Kafka-Lab-CA"

# Create the Server Private Key and CSR
openssl req -newkey rsa:2048 -nodes -keyout server.key -out server.csr -subj "/CN=test-kafka.kafka-lab.svc.cluster.local"

# Define the Subject Alternative Names (SANs) for internal DNS
echo "subjectAltName=DNS:test-kafka.kafka-lab.svc.cluster.local,DNS:test-kafka.kafka-lab.svc,DNS:localhost" > extfile.cnf

# Sign the Server Certificate
openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -CAcreateserial -out server.crt -days 365 -extfile extfile.cnf

# Load the certificates into a Kubernetes Secret
kubectl create namespace kafka-lab
kubectl create secret generic kafka-server-certs -n kafka-lab \
  --from-file=tls.crt=server.crt \
  --from-file=tls.key=server.key \
  --from-file=ca.crt=ca.crt

2. Deploy the Secure Broker Now, deploy the broker using the secret we just created. We explicitly set tls.clientAuth=none to enforce one-way SSL, bypassing the Mutual TLS (mTLS) requirement.

# Add the Bitnami repository
helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo update

# Install the secure Kafka cluster
helm install test-kafka bitnami/kafka \
  --namespace kafka-lab \
  --set replicaCount=1 \
  --set zookeeper.enabled=false \
  --set kraft.enabled=true \
  --set listeners.client.protocol=SSL \
  --set tls.enabled=true \
  --set tls.type=pem \
  --set tls.existingSecret=kafka-server-certs \
  --set listeners.client.sslClientAuth=none \
  --set image.repository=bitnamilegacy/kafka

Note: This creates a secure broker at test-kafka.kafka-lab.svc.cluster.local:9092 that encrypts traffic but does not require clients to present their own certificates.

3. Create the Backend Topic Because the broker is now expecting secure connections, we must pass a configuration file to the Kafka script so it knows to use SSL when connecting to create the topic.

Run this command to dynamically generate the client configuration inside the pod and create a topic named test-topic:

TRUST_PASS=$(kubectl get secret test-kafka-tls-passwords -n kafka-lab -o jsonpath='{.data.truststore-password}' | base64 -d) && \
kubectl exec -it test-kafka-controller-0 -n kafka-lab -- bash -c " \
  echo -e \"security.protocol=SSL
ssl.truststore.location=/opt/bitnami/kafka/config/certs/kafka.truststore.jks
ssl.truststore.password=$TRUST_PASS
ssl.endpoint.identification.algorithm=\" > /tmp/client.properties && \
  kafka-topics.sh \
  --create \
  --bootstrap-server test-kafka.kafka-lab.svc.cluster.local:9092 \
  --topic test-topic \
  --partitions 1 \
  --replication-factor 1 \
  --command-config /tmp/client.properties"

Use Case: Deploying a production-grade (but single-node) Kafka 4.1.0 cluster on EKS using the Strimzi Operator. This setup enforces Mutual TLS (mTLS) for all connections and uses internal ClusterIP networking for simplified lab testing.

1. Install the Strimzi Operator Before creating a Kafka cluster, you must install the operator that manages the Kafka custom resources.

# Add the Strimzi Helm repository
helm repo add strimzi https://strimzi.io/charts/
helm repo update

# Create the lab namespace and install the operator
helm install strimzi-kafka-operator strimzi/strimzi-kafka-operator \
  --namespace kafka-lab \
  --create-namespace

2. Deploy the Kafka 4.1.0 Cluster We will now define a Kafka custom resource. This configuration uses KRaft mode (no Zookeeper), enables mTLS on the internal listener, and targets Kafka v4.1.0. Strimzi will automatically generate the internal CAs and certificates for you.

Create a file named kafka-lab.yaml:

apiVersion: kafka.strimzi.io/v1
kind: KafkaNodePool
metadata:
  name: lab-pool
  namespace: kafka-lab
  labels:
    strimzi.io/cluster: lab-broker
spec:
  replicas: 1
  roles:
    - controller
    - broker
  storage:
    type: jbod
    volumes:
      - id: 0
        type: persistent-claim
        size: 10Gi
        deleteClaim: true
        class: gp2
---
apiVersion: kafka.strimzi.io/v1
kind: Kafka
metadata:
  name: lab-broker
  namespace: kafka-lab
  annotations:
    strimzi.io/node-pools: enabled
spec:
  kafka:
    version: 4.1.0
    metadataVersion: 4.1-IV0
    listeners:
      - name: tls
        port: 9093
        type: internal
        tls: true
        authentication:
          type: tls
    config:
      ssl.enabled.protocols: "TLSv1.3"
      ssl.protocol: "TLSv1.3"
      ssl.cipher.suites: "TLS_AES_256_GCM_SHA384"          
  entityOperator:
    topicOperator: {}
    userOperator: {}

Apply the manifest:

kubectl apply -f kafka-lab.yaml

3. Create a User for mTLS Authentication Since mTLS is enabled, the client must present a certificate signed by the Cluster CA. Strimzi’s KafkaUser resource automates this by creating a Kubernetes secret containing the user’s private key and signed certificate.

apiVersion: kafka.strimzi.io/v1
kind: KafkaUser
metadata:
  name: lab-user
  namespace: kafka-lab
  labels:
    strimzi.io/cluster: lab-broker
spec:
  authentication:
    type: tls

Apply the user manifest:

kubectl apply -f kafka-user.yaml

4. Create a Topic and Test Connection Because we are using internal networking, the broker address is lab-broker-kafka-bootstrap.kafka-lab.svc.cluster.local:9093. To create a topic, we will use the operator’s KafkaTopic resource.

apiVersion: kafka.strimzi.io/v1
kind: KafkaTopic
metadata:
  name: test-topic
  namespace: kafka-lab
  labels:
    strimzi.io/cluster: lab-broker
spec:
  partitions: 1
  replicas: 1

Apply the topic manifest:

kubectl apply -f kafka-topic.yaml

5. Extract Credentials for EEM Gateway When you configure your EEM Gateway to point to this backend, you will need the User certificate/key (to authenticate).

# Get the User Cert and Key (to be added to Gateway Keystore)
kubectl get secret lab-user -n kafka-lab -o jsonpath='{.data.user\.crt}' | base64 -d > user.crt
kubectl get secret lab-user -n kafka-lab -o jsonpath='{.data.user\.key}' | base64 -d > user.key

3.2 Connect the Backend Kafka Cluster

Once the Gateway is connected, you must tell it where to route the Kafka traffic.

  • Option A: Production (Enterprise Kafka)
  • Option B: Lab (Bitnami)
  • Option C: Lab (Strimzi)

Use Case: Connecting to AWS MSK, Confluent, or Event Streams.

  1. Navigate to the Clusters page in the EEM UI.
  2. Click Add cluster.
  3. Enter a name (e.g., prod-kafka-cluster).
  4. Enter the DNS name and port for the bootstrap server: kafka.corp:443.
  5. If certificates are set up for the Kafka broker, an error will display saying “Multiple certificates are not trusted”. Click Accept all certificates and then click Next.
  6. If your enterprise broker requires Mutual TLS (mTLS), you will be prompted on the next screen to configure your client authentication. Upload your client certificate and private key, then click Next.
  7. On the Credentials screen, if your broker uses SASL, enter those credentials here. If authentication was completely handled by your mTLS client certificates, no action is needed.
  8. Click Create to finish adding the cluster.

Use Case: Connecting to the plaintext Bitnami broker we spun up in the kafka-lab namespace.

  1. Navigate to the Clusters page in the EEM UI.
  2. Click Add cluster.
  3. Enter a name (e.g., bitnami-lab-cluster).
  4. Enter the internal Kubernetes DNS name for the bootstrap server: test-kafka.kafka-lab.svc.cluster.local:9092.
  5. Because the broker is configured for one-way SSL, you will be prompted to accept the server certificates. Review and accept them, then click Next.
  6. Since this specific lab broker does not require client certificates, bypass the client certificate upload and click Next.
  7. On the Credentials screen, since we configured the broker without client authentication, select No credentials required.
  8. Click Create to finish adding the cluster.

Use Case: Connecting to the Mutual TLS (mTLS) secured Strimzi broker we spun up in the kafka-lab namespace on EKS.

  1. Navigate to the Clusters page in the EEM Manager UI.
  2. Click Add cluster.
  3. Enter a name (e.g., strimzi-lab-cluster).
  4. Enter the internal Kubernetes DNS name for the Strimzi TLS bootstrap server: lab-broker-kafka-bootstrap.kafka-lab.svc.cluster.local:9093.
  5. EEM will detect the secure connection and prompt you to accept the server certificates provided by the Strimzi Cluster CA. Review and accept them, then click Next.
  6. On the following certificate screen, because the broker enforces mTLS, you will be prompted to provide your client certificates. Upload or paste the contents of the user.crt (Certificate) and user.key (Private Key) files you extracted earlier for the lab-user, then click Next.
  7. On the Credentials screen, select No credentials required, as authentication is fully handled by the client certificates you just provided.
  8. Click Create to finish adding the cluster and establish the secure connection.
NotePending Validation Status

After adding the cluster, you will notice its state is listed as Pending validation. This is expected! The EEM Manager is simply “waiting for a gateway group to report a validation status.” Because the Manager itself does not connect directly to the broker for data traffic, the connection cannot be actively tested until we register a Gateway and link it to this cluster in the upcoming steps.

3.3 Register the Gateway in the EEM UI

Now that the infrastructure is ready, we need to register the Gateway with the Manager. By selecting the native Kubernetes deployment option, we bypass the IBM Operator’s ingress restrictions and gain the flexibility to attach an AWS Network Load Balancer (NLB) directly to the gateway pods for raw TCP passthrough.

1. Generate the Gateway Configuration:

  • Log into the EEM Manager UI.
  • In the navigation pane, click Administration > Event Gateways.
  • Click Add gateway.
  • Select the Kubernetes Deployment tile, then click Next.
  • Provide the configuration properties for your gateway:
Field Configuration
Gateway group Create or specify an existing gateway group for your new gateway (e.g., default-group).
Gateway ID Provide an ID for your new gateway that is unique within the gateway group (e.g., eem-gateway-lab).
Replicas Set to 1 for the lab environment to create a single Kubernetes replica of the gateway pod.
Server URL Leave this field blank. We will configure the advertised listener address directly in the Gateway Custom Resource YAML later in the deployment process.
TLS Certificates Leave the Gateway private key, Gateway certificate, and CA certificate fields blank. We will map our SAN-enabled certificates explicitly in the YAML in an upcoming step.
  • Click Create to create the deployment YAML.

2. Save the Deployment Files: Following IBM best practices, copy the generated YAML and save it into two separate files so you always have an unaltered backup.

  • Save a backup copy as gateway_k8s_original.yaml.
  • Save your working copy as gateway_k8s.yaml.

Make the original file read-only to remove write permissions and avoid accidental updates:

chmod a-w gateway_k8s_original.yaml

3. Two-Phase Gateway Deployment

Because AWS dynamically generates the Network Load Balancer (NLB) hostname during provisioning, we must break the Gateway deployment into two distinct phases. You must provision the Kubernetes Service first to generate the public DNS name, and then inject that exact DNS name into the Gateway Deployment so it can correctly advertise itself to your Kafka clients.

Phase 1: Configure and Deploy the Service Extract the Service definition from your generated configuration into a new file named gateway-service.yaml. Ensure the type is set to LoadBalancer. You must also explicitly define the ports for the bootstrap server and every backend broker you intend to proxy.

Here is a sample configuration mapping the bootstrap port (443 to 8443) and two dedicated backend brokers (8444 and 8445):

kind: Service
apiVersion: v1
metadata:
  name: "default-group-eem-gateway-lab"
spec:
  ports:
    - name: kafka-client-bootstrap
      protocol: TCP
      port: 443
      targetPort: 8443
    - name: broker-0
      protocol: TCP
      port: 8444
      targetPort: 8444
    - name: broker-1
      protocol: TCP
      port: 8445
      targetPort: 8445
  type: LoadBalancer
  sessionAffinity: None
  selector:
    app: "default-group-eem-gateway-lab"
    gatewayGroup: "default-group"
    gatewayId: "eem-gateway-lab"

Apply this file to your cluster:

kubectl apply -f gateway-service.yaml

Phase 2: Retrieve the AWS NLB Hostname Watch the service until AWS provisions the NLB and populates the EXTERNAL-IP field.

kubectl get svc default-group-eem-gateway-lab -w

Copy the resulting elb.amazonaws.com hostname to your clipboard.

Phase 3: Customize the Deployment YAML Open the remaining gateway_k8s.yaml file, which should now only contain your Deployment and Secrets. Make the following six adjustments:

  1. Accept the License: Locate the ACCEPT_LICENSE environment variable and change its value to "true".
  2. Add Local DNS Routing (Lab Only): Add a hostAliases block under spec.template.spec to manually map the Manager’s IP address to your .local.test dummy hostnames. Note: You only need this block because we are using local hostnames in this lab. In a true production environment, these endpoints would be fully resolvable via your corporate DNS (like AWS Route 53), and this block should be removed.
  3. Configure TLS Versions (Optional): Add a new environment variable named TLS_VERSIONS and set it to "TLSv1.2,TLSv1.3". This prevents handshake failures if the AWS NLB defaults to an older security policy.
  4. Set the Advertised Listener: Find the KAFKA_ADVERTISED_LISTENER environment variable and set it to the exact AWS NLB hostname you copied in Phase 2, appended with port 443.
  5. Establish Manager Trust: The Gateway must securely connect to the Manager’s API to download configurations. Because Java enforces strict TLS validation, it must explicitly trust the Manager’s ingress certificate.
    • If using a Private/Self-Signed CA (Common in Labs): Replace the default string in the BACKEND_CA_CERTIFICATES variable with the exact PEM contents of the CA that signed your Manager’s ALB certificate.
    • If using a Public CA: If your Manager is fronted by a certificate signed by a widely trusted public authority (like Let’s Encrypt or DigiCert), Java will inherently trust it. In this case, you can leave the default value or remove the BACKEND_CA_CERTIFICATES variable entirely.
  6. Mount the Inbound Certificates: In the Secret blocks at the bottom of the file, populate the tls.crt and tls.key fields with your SAN-enabled certificates to secure the data plane listener.
    • Note on ca.crt: The ca.crt field is optional and is used to display the trust chain in the EEM UI for developers to download. If you choose not to provide a ca.crt here, you must also delete the entire GATEWAY_TRUST_PEM environment variable block from the pod spec above it. If you leave the environment variable looking for a secret key that does not exist, the pod will fail to start.
ImportantAWS Load Balancer TLS Compatibility

While the TLS_VERSIONS environment variable is technically optional in the base IBM documentation, it is highly recommended to explicitly set its value to "TLSv1.2,TLSv1.3" when deploying in an AWS EKS environment.

By default, AWS load balancers frequently apply conservative Security Policies that rely on TLS 1.2. Because the Gateway pod must initiate an outbound HTTPS connection to the Manager’s load balancer to download its configurations, a strict protocol mismatch here will cause the handshake to fail, preventing the Gateway from booting. Explicitly declaring TLS 1.2 ensures the Java backend can successfully negotiate the connection with standard AWS infrastructure.

Below are the complete, reference examples for both files.

gateway-service.yaml

kind: Service
apiVersion: v1
metadata:
  name: "default-group-eem-gateway-lab"
spec:
  ports:
    - name: kafka-client-bootstrap
      protocol: TCP
      port: 443
      targetPort: 8443
    - name: broker-0
      protocol: TCP
      port: 8444
      targetPort: 8444
    - name: broker-1
      protocol: TCP
      port: 8445
      targetPort: 8445
  type: LoadBalancer
  sessionAffinity: None
  selector:
    app: "default-group-eem-gateway-lab"
    gatewayGroup: "default-group"
    gatewayId: "eem-gateway-lab"
